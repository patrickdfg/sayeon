# 성령 사연 업로드

새 원고 하나를 `patrickdfg/sayeon`의 자동 게시 파이프라인에 전달하고 완료까지 확인한다. 원고 데이터·음성·동기화 파일을 직접 수정하지 않는다.

## 시작 전 확인

1. 저장소 기본 브랜치의 최신 `AGENTS.md`와 `work-upload/README.md`를 먼저 읽는다. 이 스킬과 충돌하면 저장소의 최신 지침을 따른다.
2. GitHub 연결 상태와 저장소 쓰기 권한을 읽기 작업으로 확인한다.
3. 대상은 기본적으로 2026년 성령 사연이다. 편 번호나 원고가 없거나 서로 모순되면 작업표를 만들기 전에 사용자에게 확인한다.
4. `work-upload/<편번호>.json`이 이미 있으면 덮어쓰지 말고 중단한다.

GitHub에 연결되지 않았거나 쓰기 권한이 없으면 비밀번호·토큰을 채팅으로 요구하지 않는다. 필요한 GitHub 연결, 저장소 설치 범위 또는 권한 수준을 정확히 알려 준다.

## 원고 보존

- 사용자가 채팅에 붙여 넣은 원고는 그 텍스트를 우선한다. 첨부 파일을 기준으로 하라고 명시한 경우에만 첨부 파일을 기준으로 한다.
- 줄 끝 형식만 LF(`\n`)로 통일하고, 본문의 줄 순서·줄바꿈·빈 줄을 그대로 보존한다. 맞춤법, 띄어쓰기, 문장부호, 인용부호, 후행 공백을 임의로 고치지 않는다.
- `2026년 성령 사연 <번호>` 같은 표제 줄은 메타데이터로 분리하고 `content`에는 본문만 넣는다. 표제가 본문인지 불분명하면 묻는다.
- 편 번호가 원고 표제와 사용자 요청에서 다르면 추측하지 않는다.
- 작업표에는 `content` 문자열을 사용한다. JSON 직렬화 때문에 화면상 `\n`으로 보여도 복원된 문자열의 줄바꿈과 빈 줄이 원문과 같아야 한다.

## 작업표

기본 형식은 다음과 같다.

```json
{
  "category": "sayeon",
  "year": 2026,
  "no": 168,
  "title": "성령 사연 168",
  "content": "첫 문단 첫 줄\n첫 문단 둘째 줄\n\n둘째 문단"
}
```

- 경로는 `work-upload/<편번호>.json`이다.
- 기존 편을 덮어쓰지 않도록 기본 작업표에 `replace`를 넣지 않는다.
- 사용자가 기존 편 교체를 명확히 요청한 경우에도 대상과 의도를 다시 확인한 뒤에만 `"replace": true`를 넣는다.
- 커밋 전 `scripts/validate_job.py <작업표>`로 구조를 검사한다. 의도적인 교체만 `--allow-replace`를 추가한다.

## 게시 및 확인

1. 대상 파일이 없음을 최신 main에서 다시 확인하고, 새 파일 생성 방식으로 main에 커밋한다. 기존 파일 갱신 API를 사용하지 않는다.
2. 푸시 충돌이나 브랜치 변경이 감지되면 강제 푸시하지 않는다. 최신 main을 다시 읽고 대상 파일의 부재를 재확인한다.
3. GitHub Actions가 다음 작업을 수행하게 둔다: 데이터 추가, 현수 TTS 생성, 문단 시간표 생성, 결과 커밋, Pages 재배포.
4. 관련 워크플로가 queued/in_progress이면 완료될 때까지 상태를 확인한다. 60초 이상 기다릴 때는 사용자에게 진행 상황을 알린다.
5. 성공 판정은 최소한 다음을 확인한다.
   - 자동 게시 워크플로 결론이 success다.
   - 작업표가 처리 후 삭제됐다.
   - `audio/<편번호>.mp3`가 생성됐다.
   - 이어진 Pages 배포가 success다.
   - 가능하면 실제 사이트에서 해당 편이 열리는지 확인한다.
6. 실패하면 실패한 단계와 로그의 핵심 원인을 보고한다. 실패한 워크플로를 임의로 반복 실행하거나 직접 결과 파일을 만들어 우회하지 않는다.

완료 보고에는 편 번호, 작업표 커밋, 자동 생성 커밋 또는 워크플로 실행, Pages 배포 결과를 간단히 포함한다.

## 다른 AI에서 사용

이 폴더는 Codex용 `agents/openai.yaml`을 포함하지만 핵심 절차는 이 `SKILL.md`와 Python 검증기에만 있다. 다른 AI 도구에서는 이 파일 전체를 작업 지침으로 먼저 읽게 하면 된다. 해당 도구가 GitHub 파일 생성과 Actions 상태 조회를 지원하지 않으면 로컬 Git 또는 GitHub CLI로 같은 절차를 수행하되, 사용자 계정에 이미 설정된 인증만 사용한다.
